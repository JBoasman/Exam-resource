# Q4 - Reliable, efficient, maintainable software

Start by making reliability and performance requirements measurable: define acceptable failure rates, latency, throughput, and resource limits for realistic workloads. Agree on interfaces and contracts before implementation so that modules have explicit responsibilities and invalid inputs are handled consistently. High cohesion and low coupling localise changes; depending on abstractions allows implementations to change without modifying every client. For example, a repository interface separates application logic from XML persistence, and a Strategy separates a delivery quote calculation from its caller.

Choose data structures from the operations the application performs. A balanced search tree bounds search and insertion costs logarithmically, while a hash table suits exact-key lookup when ordering is unnecessary. Measure representative workloads with a profiler before optimising, because faster code in an irrelevant path does not improve user-visible latency. Check that caching does not return stale data and that concurrency does not compromise correctness.

Use version control, small reviewed changes, and automated builds to make changes reproducible. Unit tests cover boundaries, branches, and invalid inputs; integration tests check interactions such as parsing and persistence; end-to-end tests validate important user workflows. Test coverage reveals unexecuted code but does not prove correctness, so assertions must reflect requirements.

Refactor duplication and unclear responsibilities while the regression suite checks preserved behaviour. Document contracts and non-obvious design decisions rather than repeating the code. Monitor deployed failures and performance, then feed that evidence into tests and design changes. These practices reinforce each other: modular code is easier to test, reliable tests enable safe refactoring, and measured optimisation preserves maintainability while improving the performance that matters.
